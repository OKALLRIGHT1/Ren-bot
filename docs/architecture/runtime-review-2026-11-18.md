## 一、群状态回收（已修复）

审查基线中，每个群的历史行数有上限，持有所有群状态的字典却只增不减。现在默认保留最近使用的 256 个群，空闲 1 小时回收，实际过期时间至少覆盖配置的最长退避窗口。事件循环用一个定时器处理空闲队列，即使再无消息也会清理。同步入口在访问时清理。等待模型的群单独保留，所有群都在等待时可以暂时超过容量，决策结束或取消即收缩。[状态与回收逻辑](../../services/chat_support/group_reply_planner.py#L549)

**同一负载的前后对照。** 从空规划器开始，每群调用一次 `note_assistant` 并发送相同短消息。创建规划器后开启 `tracemalloc`，垃圾回收后读取存活分配。1,000 个群时由 1,000 项、1.01 MiB 降到 256 项、约 0.28 MiB。10,000 个群时由 10,000 项、10.00 MiB 降到 256 项、约 0.29 MiB。这是无模型调用的合成负载，仅衡量 Python 跟踪内存。[群聊回归测试](../../tests/test_group_reply_planner.py)

## 二、群聊配置复用（已修复）

此前入站决策与出站回复各自打开并解析设置文件。现在 QQ 私聊和桌面消息在创建规划器、取角色称呼和插件关键词之前就返回。群聊入站和出站共用同一份解析结果。进程内成功写入设置后，下一次群聊访问立即读入新值。手工修改或其他进程写入时，访问方每秒最多检查一次文件元数据，发现变化再解析。保存失败或读到残缺 JSON 时继续沿用最近的有效配置。[入站入口](../../services/chat_service.py#L2585) · [出站入口](../../services/chat_service.py#L1035) · [配置快照](../../services/chat_support/group_reply_planner.py#L350)

回归用例连续进行五轮群聊决策和回复，只触发一次配置读取。成功保存后下一条群消息应用新开关，失败保存不触发重读。外部文件先写坏、再修复的情况同样有覆盖。[配置回归测试](../../tests/test_group_reply_planner.py)

## 三、记忆关键词召回的主要成本在排序和取前 K 条之前

作用域索引可先缩小记录范围。随后，每个候选都要对每个查询词执行一次或多次 `instr(lower(content || ' ' || key), ?)`，还要判断有效期并按命中数排序。查询词上限为 96。生产方法的查询计划显示使用 `idx_memory_records_scope`，并出现 `USE TEMP B-TREE FOR ORDER BY`。结果上限为 20 也不能省掉前面的匹配。[实际查询构造](../../modules/memory_core/repository.py#L1750)

| 同一作用域的有效记录 | 1 个词 | 8 个词 |
| ---: | ---: | ---: |
| 1,000 | 0.92 ms | 3.04 ms |
| 10,000 | 8.63 ms | 31.49 ms |
| 50,000 | 60.82 ms | 213.01 ms |

**复测方法。** 在临时 SQLite 库用 `MemoryCoreRepository.initialize()` 创建正式表及索引。批量写入同一 owner、同一 session 的短 episode，每百条有一条包含 `target`，其余为 `sample text noise`，有效期为空。调用 `search_current_records(limit=20)`，分别传入 `target` 或追加 7 个无命中的词。每档预热一次，再取七次耗时的中位数。该数字只覆盖本地关键词查询与结果转换。短文本、单作用域和热缓存均会影响外推。

**建议。** 先用真实查询词数和每个作用域的可见行数确定慢查询分布。若大库常见，评估由子串索引生成候选 ID，再用原有 SQL 精排。对中文双字、单字符、标点和跨 content/key 拼接的查询保留完整回退，避免引入漏召回。用同一数据集对照结果 ID、顺序、写入成本、索引体积和查询 p95。仓库已有覆盖旧记录、低权重记录、字面标点与过期过滤的[回归用例](../../tests/test_memory_retrieval_coverage.py)。

**实体度数查询已修复。** 实体召回原先为每个命中实体单独执行关系计数，默认最多 20 次。现在对命中的实体 ID 用一条 SQL 分组计数，取各组的最大度数。保留原有主体范围、有效状态与关系类型筛选，最大度数超过 50 时启用图排序。回归用例在双实体命中时记录 SQLite 实际执行的语句，验证仅执行一条计数查询，并覆盖最大度数为 50 和 51 的边界。[召回调用](../../modules/memory_core/service.py#L1420) · [批量计数](../../modules/memory_core/repository.py#L2356) · [回归测试](../../tests/test_memory_reliability.py)

**关联记忆过滤顺序已修复。** 同一实体关联 41 条记忆时，如果前 40 条全部过期、尚未生效或种类不符，旧实现会返回空结果。现在 SQLite 先筛选主体、会话、状态、种类及有效期，同一条记忆命中多个实体只计一次，再按确认时间取最近 40 条。有效期与关键词查询共用同一条件，起点包含、终点排除。三种样本在修复前均漏召回，修复后都只返回第 41 条。回归用例还覆盖带时区的日期、旧库不规范日期、全局共享和跨群隔离。[实体召回](../../modules/memory_core/service.py#L1427) · [关联查询](../../modules/memory_core/repository.py#L2308) · [回归用例](../../tests/test_memory_retrieval_coverage.py)

## 四、桌面启动、首次回复与向量检索（已优化）

关闭语音、开启嵌入时，聊天窗口提前 **1.03 秒**可用，窗口就绪时少用 **55.5 MiB**。启用向量的普通聊天会在生成回复前检索记忆，所以同一轮里先记录检索命中，再记录回复显示。下表是每种配置各 5 个全新进程的中位数，时间从父进程启动 Python 子进程前开始计算，内存为各事件发生时主进程的工作集（RSS）。

| 嵌入配置 | 观测点 | 基线累计时间 | 优化后累计时间 | 基线工作集 | 优化后工作集 |
| --- | --- | ---: | ---: | ---: | ---: |
| 关闭 | 聊天窗口可输入 | 3.146 s | 2.165 s | 184.9 MiB | 137.4 MiB |
| 关闭 | 首条普通回复显示 | 3.514 s | 2.555 s | 255.6 MiB | 207.8 MiB |
| 开启 | 聊天窗口可输入 | 3.203 s | 2.176 s | 193.2 MiB | 137.7 MiB |
| 开启 | 首次向量检索命中 | 3.551 s | 3.397 s | 263.9 MiB | 257.5 MiB |
| 开启 | 首条普通回复显示 | 3.569 s | 3.417 s | 264.4 MiB | 259.9 MiB |

**首用代价。** 开启嵌入时，从调用检索到返回命中由 **3 ms 升至 886 ms**，从点击发送到收到回复由 **0.379 s 升至 1.242 s**。大部分差异来自首次打开 Chroma。若从打开程序开始计时，含向量检索的首条回复仍提前约 0.15 s。关闭嵌入时，从发送到回复为 0.377 → 0.391 s，首条回复显示时节省 47.8 MiB。5 次开启嵌入的窗口就绪时间分别落在 3.16–3.24 s 和 2.12–2.21 s。

**加载边界。** SQLite 记忆、短期历史和嵌入配置在启动时就绪。Chroma 客户端按首次访问创建，当前记忆索引、知识库及旧版记忆集合各自按需打开。后台索引调度先查 SQLite，空队列直接返回，有待办时仍会在重启后自动恢复。并发请求共用首次成功创建的对象，创建失败可以重试。旧版图谱读取和 NetworkX 加载推迟到实际使用图谱时。高连接度实体的排序仍按原逻辑运行。文本模式可读取语音设置、创建 PCM 限流器，只有使用识别引擎或语音传感器接口才需要加载相应后端。测试验证了重启补索引、首次操作即重建、并发和失败重试，以及 Qt 收到真实聊天流水线回复时的模块加载状态。[记忆资源与调度](../../modules/advanced_memory.py) · [语音包入口](../../modules/asr/__init__.py) · [回归测试](../../tests/test_memory_lazy_startup.py)

**测量与复现。** Windows build 26200，Core i7-14700，Python 3.11.18，PySide6 6.12.0，Chroma 1.5.9。基线为 `fbc2255`，两版使用同一脚本和虚拟环境。每轮从临时数据副本启动 `boot.main()`，工作目录复制主仓库自带的 5 个插件，使用默认角色配置。SQLite 和持久化 Chroma 含同一条已索引记忆。Qt 在 offscreen 平台展开面板，处理事件并确认输入框可见可用，然后提交「你好呀」。回复计时止于助手文本写入 Qt 聊天记录。向量计时止于真实 Chroma 查询返回预置记忆。模型输出和嵌入固定，TTS、外部服务、渲染器、设备采集及全局热键关闭。结果涵盖应用进程及其聊天流水线，系统文件缓存可复用。线上模型延迟、显示器实际呈现、外部进程内存与峰值 RSS 需另测。[基准脚本](../../benchmarks/startup.py)

装好项目依赖后，在仓库根目录运行以下命令即可复测。

## 六、相关开源项目有哪些做法值得借鉴

### 消息路径与群状态：NoneBot、python-telegram-bot

**配置的加载者和使用者可以分开。** NoneBot 的插件示例在加载时取得类型化配置，处理消息时读取已有对象。Ren-bot 已经有 `GroupReplyPlannerConfig`，最小改动是让设置层在保存成功后替换这份快照。每次群聊决策开始时取一次引用，整轮沿用；私聊在准备关键词之前就返回。这样仍能在桌面改完设置后立即生效。验证时可在两条群消息之间切换开关，再用一次保存失败确认旧配置仍可用。[NoneBot 配置示例](https://nonebot.dev/docs/2.4.3/appendices/config) · [Ren-bot 群聊配置入口](../../services/chat_support/group_reply_planner.py#L350)

**缓存应有总容量，淘汰时还要考虑谁正在用它。** python-telegram-bot 用有容量上限的 LRU 缓存保存回调数据，并提供按最近访问时间清理的入口。它处理的是按钮回调。Ren-bot 的群状态还承载退避和等待中的模型决策，适合先淘汰最久未使用且没有决策在途的群。若所有候选都在使用，可以暂缓淘汰，在决策结束时再收缩。容量按实际活跃群数选取。回归场景可固定为 A 群等待模型、B/C 群填满缓存、A 群收到结果，核对 A 的退避仍只更新一次，随后缓存回落到上限。[python-telegram-bot 缓存源码](https://github.com/python-telegram-bot/python-telegram-bot/blob/master/src/telegram/ext/_callbackdatacache.py) · [Ren-bot 群状态](../../services/chat_support/group_reply_planner.py#L549)

### 记忆检索：sqlite-utils 的索引维护，SQLite 的子串匹配

sqlite-utils 把建全文索引、填充历史行、维护更新触发器和重建索引做成独立操作。Ren-bot 已有 FTS5 表及增删改触发器，现有关键词路径仍使用字面子串匹配。若试验 trigram，先按生产查询的同一表达式索引 `content || ' ' || key`，覆盖跨字段的文本；再做历史行回填和更新、删除、重建的一致性测试。这样能单独验证索引生命周期，也能在旧库迁移中断时继续使用现有查询。[sqlite-utils 索引实现](https://github.com/simonw/sqlite-utils/blob/main/sqlite_utils/db.py) · [Ren-bot 现有 FTS 表和触发器](../../modules/memory_core/repository.py#L267)

**本地小实验改变了索引的验收条件。** 在项目虚拟环境新建内存 FTS5 trigram 表，依次写入“星河预算”“单列预算”“a_b 100%”，对比带引号的字面量 `MATCH` 与现行 `instr`。结果如下。SQLite 规定 trigram 全文匹配的查询片段至少包含三个 Unicode 字符。[SQLite trigram 说明](https://sqlite.org/fts5.html#the_trigram_tokenizer)

| 查询词 | trigram 命中行数 | 字面子串命中行数 |
| --- | ---: | ---: |
| 星河预 | 1 | 1 |
| 预算 | 0 | 2 |
| a_b | 1 | 1 |
| % | 0 | 1 |

#### 5 万条中文记录的索引对照实验

**单用 trigram 会漏掉全部单字和双字查询。** 在长短词混合时，仅比较前 20 条也容易得出错误结论。例如“乌龙茶 + 预算”的前 20 个 ID 及顺序与基线相同，但全部 1,949 个有效命中只找回了 778 个。含短词就回退到现有 SQL 可找全，速度也回到扫描水平。

另一种实验方案把基本汉字的单字和相邻双字独立建 FTS5 索引，三字及以上使用 trigram。混合查询先合并两路 rowid、去重，再按原有的作用域、有效期、命中词数和优先级排序。SQLite 执行计划显示先合并索引候选，再按主表 rowid 取记录。这条路径在下列六组样本中，全量 ID 集合、前 20 个 ID 及顺序均与现行查询一致。[可复现基准](../../benchmarks/memory_keywords.py)

| 查询词 | 基线命中数 | 仅 trigram 找回 | 现行查询 p50 / p95（ms） | 单双字索引 + trigram p50 / p95（ms） |
| --- | ---: | ---: | ---: | ---: |
| 茶 | 1,169 | 0 | 65.82 / 75.60 | 4.23 / 7.71 |
| 预算 | 1,560 | 0 | 68.20 / 92.61 | 4.77 / 10.45 |
| 乌龙茶 | 778 | 778 | 64.72 / 82.13 | 2.32 / 4.59 |
| 乌龙茶 + 预算 | 1,949 | 778 | 98.22 / 134.24 | 9.15 / 12.50 |
| 星河预算，经内置滑窗展开为 6 个词 | 1,560 | 779 | 195.16 / 225.53 | 16.23 / 19.86 |
| 记录，命中全部可见行 | 38,961 | 0 | 95.65 / 107.73 | 105.24 / 125.96 |

**复测方法。** 在仓库根目录、项目虚拟环境下运行 `python -m benchmarks.memory_keywords`。脚本使用临时数据库、固定生成的 50,000 条短文本和正式表结构，当前主体及会话可见 38,961 条。复用生产仓储生成的 SQL，以字面子串结果为基准。全量集合单独验证，计时只取前 20 条，包含 SQL 执行及读取结果 ID。四条查询路径轮换顺序，各预热 2 次、测量 30 次。单字输入直接传给关键词仓储，日常对话的中文滑窗从双字开始。数据为 Windows、SQLite 3.53.1 的一次热缓存测量，未计分词、向量检索或模型响应。[生产分词入口](../../modules/memory_core/service.py#L1552) · [生产 SQL 计分](../../modules/memory_core/repository.py#L1805)

#### 写入成本、扫描交叉点与生产开关

**单双字索引已接入主程序，默认关闭。** 适合有较大中文会话、经常查找少见词的部署。设置环境变量 `MEMORY_KEYWORD_INDEX_ENABLED=1` 并重启，记忆库初始化时会在一个事务中回填旧行并安装维护触发器。设为 `0` 并重启会移除派生索引及其触发器。SQLite 缺少 FTS5 时继续使用字面扫描。[配置](../../config.py) · [索引维护与查询选择](../../modules/memory_core/keyword_index.py)

**写入开销。** 在四个独立的临时库中分别测现行写入、上一轮的单双字原型、单双字加 trigram 原型和生产实现。四库均保留原有 FTS 与向量任务机制，每次调用仓储的新增、正文与键修改、元数据修改或删除接口并独立提交。按固定种子生成 24 或 256 个汉字，写入顺序在四个库间轮换，前 10 次预热，每项计时 140 次。下表是第二次独立运行的单条耗时，单位 ms。

| 字数 | 操作 | 索引关闭 p50 / p95 | 生产索引开启 p50 / p95 | p50 增量 |
| ---: | --- | ---: | ---: | ---: |
| 24 | 新增 | 0.399 / 0.778 | 0.545 / 1.167 | +0.146 |
| 24 | 修改正文和键 | 0.308 / 0.501 | 0.505 / 0.917 | +0.197 |
| 24 | 删除 | 0.220 / 0.473 | 0.376 / 0.713 | +0.156 |
| 256 | 新增 | 0.408 / 0.770 | 0.895 / 1.460 | +0.487 |
| 256 | 修改正文和键 | 0.393 / 0.645 | 0.992 / 1.908 | +0.599 |
| 256 | 删除 | 0.312 / 0.656 | 0.549 / 1.048 | +0.237 |

仅修改元数据时，触发器会跳过重建，256 字样本的中位耗时为 0.227 ms（关）和 0.222 ms（开）。两次独立运行中，256 字正文修改增加 0.60–0.63 ms。12,000 条旧记录的首次回填耗时 0.27–0.29 秒，数据库增加 3.34 MiB。双索引原型在 24 字正文修改时的 p95 达到约 4.7–4.9 ms，生产实现因此只维护一张单双字候选表。表和触发器只用 SQLite 内置功能，另一个连接写入、回滚或删除记录时也会同步生效。

**高频到什么程度适合扫描，取决于会话大小。** 把 12,000 条记忆分在 120、1,200、10,680 行三个会话，测八档全库词频（约 1%、5%、15%、30%、50%、70%、90%、100%）。每档轮换执行扫描、强制索引和生产自动选择，预热 2 次后测 20 次，逐轮核对前 20 个 ID 及顺序。120 行会话在 5% 时强制索引已经较慢；1,200 行会话的交叉点在约 30%；10,680 行会话在约 90% 时两条路径接近，100% 时扫描较快。下表使用第二轮结果。自动耗时包含选择路径、精排和结果转换。

| 会话行数 | 全库候选数 | 纯扫描 p50 / p95（ms） | 自动选择 p50 / p95（ms） | 实际路径 |
| ---: | ---: | ---: | ---: | --- |
| 120 | 603 | 0.227 / 0.287 | 0.277 / 0.359 | 扫描 |
| 1,200 | 603 | 1.117 / 1.205 | 0.626 / 0.735 | 索引 |
| 1,200 | 3,522 | 1.291 / 1.373 | 1.511 / 1.790 | 扫描 |
| 10,680 | 114 | 8.492 / 9.743 | 0.930 / 1.170 | 索引 |
| 10,680 | 5,943 | 10.596 / 11.165 | 7.928 / 9.527 | 索引 |
| 10,680 | 12,000 | 12.978 / 13.646 | 13.599 / 15.102 | 扫描 |

**生产规则取保守值。** 先按状态、主体、会话和种类计数，最多看 8,192 条；少于 512 条直接扫描。其他情况允许的全库候选数为上述计数的 75%，最多 6,144 条，探测到超出一条就回退。分母取有效期过滤之前的数量，最终查询仍检查有效期。这个阈值会放弃一部分靠近交叉点的收益，也会产生探测成本。例如全库高频词在大会话中回退时，本次中位耗时比强制扫描多 0.62 ms。这也是开关默认关闭的原因。

**检索语义。** 每个查询词优先选取其中一对相邻的基本汉字，其次取单字，任一词缺少汉字就整次扫描。SQL 对候选继续执行原有字面匹配、有效期和范围过滤及排序。正文与键拼接超过 384 个字符或含 NUL 的行只写入兜底标记，每次候选查询都包含这些行。这样能限制长文本的写入成本，又能找回出现在末尾的词。单字、双字、混合词、跨字段文本、旧行回填、跨连接写入及事务回滚均有[回归用例](../../tests/test_memory_keyword_index.py)。

**复现。** 在项目虚拟环境运行 `python -m benchmarks.memory_keyword_costs`。输出写入四组及读取三组的 p50/p95、全库候选数、自动选择路径和回填成本。环境为 Windows、SQLite 3.53.1、热缓存，使用合成语料，耗时不含后台向量计算与模型调用。此表中的两次运行均使用独立新建的数据库。[写入和交叉点基准](../../benchmarks/memory_keyword_costs.py)

### 插件边界：AstrBot 的配置表单，MaiBot 的会话接口

**通用表单与插件专属操作可分别演进。** AstrBot 让普通设置通过 schema 呈现，带运行状态、文件和交互流程的功能可以由插件提供独立视图。Ren-bot 已会读取字段 schema，但通用编辑器内仍有 `knowledge_base` 分支和“保存并导入知识”动作。建议先让同一份字段描述驱动 Qt 控件的读取、校验和写回，再把知识导入收敛为具名操作。这个改动可沿用 Qt 和现有插件格式。验收时用旧配置往返一次，检查未知字段保留、取消编辑不会启动导入、普通插件不创建知识导入控件。[AstrBot 插件视图指南](https://docs.astrbot.app/en/dev/star/guides/plugin-pages.html) · [Ren-bot 专属分支](../../modules/gui/dialogs/plugin_manager.py#L1747) · [知识导入动作](../../modules/gui/dialogs/plugin_manager.py#L4417)

**会话访问与结果投递应各有清楚的接口。** MaiBot SDK 允许插件通过 chat 接口定位会话，再向指定会话发送结果。对 Ren-bot 的后台智能体，值得沿用的是“提交任务时确定目标”这一点。主人的 QQ 私聊与桌面共享历史和任务访问权，发起渠道仍决定完成通知送到哪里。重构应用层时可把这条约定固化为跨渠道测试：从 QQ 提交，在桌面查看，完成时只向最初的 QQ 会话投递一次；群聊无法读取该任务。这样能检验宿主通信接口是否足够窄，也能保护已有行为。[MaiBot SDK 会话与发送示例](https://github.com/Mai-with-u/maibot-plugin-sdk/blob/main/docs/guide.md) · [Ren-bot 会话任务隔离](../../core/application.py#L3599)
